Orders and manage map

What a guest sees after paying: the order confirmation with its status poller, and the manage page for cancelling or moving a booking. Both live in one route group, share one frame, and neither reads a cache. Traced from the code on main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache', tagged for invalidation
Streamed per request, behind a Suspense fallback
Client island 'use client', hydrates
Server action called from an island or a form
Pure lib plain function in src/lib

Nothing on these pages is a cached read and nothing is streamed: there is no 'use cache', cacheTag, cacheLife or Suspense boundary in either route. Both pages are per-request and every read is behind a secret in the address.

What arrives when

  1. One response per page. Neither page has a Suspense boundary, so the shell and the body arrive together after the order read. The only thing that streams separately is RenderPerRequest, which renders nothing.
  2. Hydration. Confirmed receipt: only SiteMenu. Pending order: SiteMenu and OrderStatusPoller. Manage: SiteMenu and the Button module, which ships because ManageBooking imports it.
  3. Pending to settled. The poller asks getOrderStatus on its timer. When the state is anything but pending, it shows one announcement and calls router.refresh(). The server component runs again, re-checks the token, and swaps the poller for the receipt or notice.

How the token is handed over

  1. Checkout sends the paying device to /orders/<ref>?t=<order token> (orderConfirmationPath in src/lib/routes.ts).
  2. src/proxy.ts sees the token on that path, sets the ramble_order_access cookie (HttpOnly, SameSite=Lax, path scoped to that order, two hours), and answers with a 303 to the same address with no query.
  3. The page reads the cookie first and checks the token against the order anyway, so the cookie has no more power than the link.
  4. The receipt then offers the manage token, and the confirmation email carries it too. /manage/<token> has no cookie: the token stays in the address.

Guest cancel and move through the actions

  1. The guest opens /manage/<token>. readManagePage spends a try, finds the booking and builds the refund from the same quote the action checks.
  2. Cancel: The cancel button, labelled with the refund, links to ?confirm=1. The form posts Server action cancelBookingForm with the token and expectedRefundMinor. If the refund has changed since the page was drawn, nothing is cancelled and the page says "The refund has changed".
  3. Move: The move link (prompt.linkLabel) goes to ?move=1, which makes the read include other dates. The form posts Server action moveBookingForm with targetSessionId. The price stays the same.
  4. Both forms redirect() back to the same page with a short code in the query (?result= or ?moved=). The page turns the code into the notice, and a stale or odd value shows nothing.
  5. Every refusal (bad shape, unknown, stale version) is not_found. Over the limit is rate_limited with a wait time.

How its caches are cleared

These pages hold nothing in the cache and nothing is cleared for them: the next view always reads the database, and both routes send Cache-Control: no-store through tokenRouteHeaders in the proxy. The actions do reach out the other way. A cancel that goes through, or a move, calls revalidateTagsForChanges with a spaces change for each affected session, which clears the session tag of that date so the experience page's sold-out and spaces-left reads rebuild. A refused or unchanged result clears nothing. Note these use revalidateTag(tag, 'max'), not updateTag, so the next experience-page view may still be served the old spaces count once while it rebuilds.

Worth knowing

  • The header here never knows who is signed in. GuestShell gets no account slot in (site)/layout.tsx, so a signed-in guest sees "Sign in" on both pages. The experience page streams HeaderAccount; these pages do not.
  • No src/app/layout.tsx. The (checkout) layout draws the document itself, so the html, fonts and CSS for these pages come from there, not from a root layout.
  • The order token crosses into the browser for a pending order. The cookie is HttpOnly, but OrderStatusPoller receives the raw token as a prop so it can pass it to the action. It is only sent for the pending state.
  • The page and the poller never share a verdict. The poller only decides "keep asking" or "re-render". The page re-checks the token and rebuilds the view, so a status can never show on the poller that the server would not show.
  • Each manage view costs one try. The page and both actions share the manage limit, so refreshing the page counts, and a guest who reloads a lot hits the too-many-tries screen with no booking on it.
  • A shared version voids both links. The order and manage tokens are derived from the same row and manage_token_version, so one bump kills the confirmation URL and the manage link together.
  • Catch-alls return 200. notFoundPerRequest cannot change the status of a render resumed from the empty shell, so /orders and /manage are 200 pages that show the not-found notice. A wrong token on the real routes goes through the same path.
  • Button is a client module, ButtonLink is not. ManageBooking and OrderConfirmation are server components, but the submit and "Check again" buttons are client code. The receipt's four action links ship no JS.
  • The calendar file is not a route. It is a data URI built at render time, so the whole event sits inside the page's HTML.
