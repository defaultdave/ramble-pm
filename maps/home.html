Home page map

How the home page is assembled: every component from the layout down, where it runs, what it reads, and how the search form reaches the browse page. This page has no server actions and no page-specific client islands. Traced from the code on main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache', tagged for invalidation
Streamed per request, behind a Suspense fallback
Client island 'use client', hydrates
Server action called from an island
Pure lib plain function in src/lib

What arrives when

  1. Shell. Layout, skip link, header, footer, and the HomeSkeleton. The header shows signed-out. No page content is in the shell, because HomeContent waits for the request before it reads anything.
  2. Streamed in. The banner and the signed-in account control replace their fallbacks. HomeContent replaces the skeleton in one piece: hero, rails, Picks, gift guide, this week and the reassurance row arrive together, not one by one.
  3. Hydration. Two islands: SiteMenu and the hero's submit Button. The search form, the chips and every card link work with scripting off.

The one user path: the hero search

  1. The guest picks a neighborhood, a day and a party size. Nothing runs in the browser; these are plain form fields.
  2. Submit is an ordinary GET to /new-york/browse, with neighborhood, date and guests in the address. The browse page reads them.
  3. No server action runs on this page. Category chips, Pick cards, "See all" and the gift guide button are links.

Cache invalidation

Five cached reads feed this page, on five kinds of tag. Each change goes through tagsForChanges() in src/lib/cacheTags.ts.

  • Home modules saved (homeModules) clears home, and so does a Pick or gift guide change, which also clears its own pick:<slug> or gift-guide tag. That rebuilds getHomeContent.
  • An experience's sessions or photos change clears experience:<id>. That reaches getHomeContent, getThisWeek and getCoverPhotos for any card that shows the experience. getHomeContent tags every ID a Pick names, even one a guest cannot see yet, so publishing it adds its card.
  • A listing is published, edited or taken down also clears catalog, which is what getThisWeek is tagged with, and the experience's own tag.
  • Settings saved clears settings: the banner, and the gift guide module's on/off.
  • Category or neighborhood names: taxonomy has no change kind that reaches it, so a new name shows when the editorial profile runs out (revalidate 1 hour).
  • Bookings: a booking or hold publishes only session:<id>, which nothing on this page carries. "On this week" catches up when its minute-keyed entry rolls over, about 60 seconds.

Worth knowing

  • The whole page is streamed. HomeContent calls connection() before anything, so even the cached editorial content never reaches the static shell. Every visitor first sees HomeSkeleton. The comment gives the reason: the day and the week are request-time values.
  • The "On this week" cards bring their own covers, the Picks cards do not. getHomeContent reads with covers: false, then HomeContent makes a second read through readGuestCovers. getThisWeek reads with covers: true. Two ways of getting a cover on one page.
  • A cover failure is silent, a content failure is not. A failed cover read renders cards without images; a failed content read shows PageError. A failed settings read inside this try block also shows PageError, although the banner, which reads the same entry, quietly hides itself.
  • The only page-level client code is a submit button. Button is 'use client', and the hero is otherwise all server. SiteMenu is the other island, and it comes from the shell.
  • The gift guide depends on two switches. It needs giftsEnabled (settings, 5 minute revalidate) and a module row, so turning gifts off hides it only after the settings entry is cleared, and the home entry itself does not carry the settings.
  • No root layout file. (guest)/layout.tsx renders <html>. Each route group (guest, checkout, host, ops) has its own, so html-level changes are made per group.
  • The h1 can come from three places: the hero, HomeTitle (no hero), or the skeleton's hidden one while loading. HomeEmpty has its own through PageHeading.
