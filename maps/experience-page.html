Experience page map

How the experience page is assembled: every component from the layout down, where it runs, what it reads, and how the booking islands reach the server. Traced from the code on main, 2026-11-14, rechecked 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache', tagged for invalidation
Streamed per request, behind a Suspense fallback
Client island 'use client', hydrates
Server action called from an island
Pure lib plain function in src/lib

What arrives when

  1. Shell. Layout, header, gallery and every section, from the cached page data. The header shows signed-out, the dates and booking slots show skeletons.
  2. Streamed in. The banner, the signed-in account control, the upcoming dates and the booking controls each replace their fallback as they finish. They read the clock and the address's ?date=, which is why they can't be part of the cached shell.
  3. Hydration. Five islands wake up: SiteMenu, GalleryStrip, StickyAside, and the bar and sheet or the panel. With scripting off, everything but those still renders.

Pressing Continue

  1. Bar, sheet and panel all call useBookingDraft(offer). One module-level store, keyed by experience id, through useSyncExternalStore, so a date picked in the sheet is already picked in the panel.
  2. submit calls Server action reserveSpaces in src/server/actions/holds.ts. The bot check and the device's try limit run first.
  3. A held booking routes to /checkout/<holdId>. Sold out or a lost race comes back as an effect the islands show, with nearby alternatives.

Cache invalidation

Both reads for this page share the tag experience:<id>. Publishing an edit, seat changes (through src/server/spacesLeft.ts) and the pulse job all go through tagsForChanges() in src/server/cache/invalidate.ts, which clears that tag, and the next request rebuilds the shell and the session lists. Site settings (bookings paused, gifts on) have their own settings tag. Cached code never reads who is signed in: that is what the streamed HeaderAccount is for.
