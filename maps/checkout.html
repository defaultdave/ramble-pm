Checkout page map

How the checkout page is assembled and how a held booking becomes a paid order: every component from the root layout down, the payment path through the fake gateway and its webhook, and the hand-off to the order confirmation page. Traced from the code on main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache', tagged for invalidation
Streamed per request, behind a Suspense fallback
Client island 'use client', hydrates
Server action called from an island
Pure lib plain function in src/lib or src/server

Nothing on this page is streamed: the route has no Suspense boundary. The whole page is one request-time render.

The payment path

In order, from the hold to the confirmation page.

  1. reserveSpaces()Pure lib
    src/server/db/holds.ts
    The hold. Made earlier by the reserveSpaces action on the experience page; it writes holds and holdItems for the device and takes the seats. Its id is the address of this page.
  2. startPaymentServer action
    src/server/actions/checkout.ts
    Hold becomes an order plus an attempt, and a payment with a client secret. See the tree above.
  3. confirmFakePaymentServer action
    src/server/actions/fakePayment.ts
    The guest's card step reaches the fake gateway.
  4. getFakePayments().confirm()Pure lib
    src/server/ports/payments/gateway.ts · fake.ts
    Records the outcome and returns the event it emitted (payment.succeeded, a decline, or a 3-D Secure step). A retry of a success recalls the stored event through lastEventFor().
  5. deliverFakeConfirmation()Pure lib
    src/server/fakePaymentDelivery.ts
    Signs the event with signWebhook() and builds a Request to http://localhost/api/webhooks/payments that is never sent over the network; it is passed straight to takePaymentWebhook().
  6. takePaymentWebhook()Pure lib
    src/server/paymentWebhook.ts
    The same intake the real route uses: size cap, verifyWebhook() on the raw body, rate limits (payment_webhook_failed by address, payment_webhook overall), then recordProviderEvent(), which stores the event once with its job process-provider-event.
  7. POST /api/webhooks/paymentsServer
    src/app/api/webhooks/payments/route.ts
    The real door, one line: paymentWebhookResponse(request). The fake path above does not call it. A real provider would.
  8. drainJobs() then handleProviderEvent()Pure lib
    src/server/jobs/drain.ts · providerEvents.ts
    Runs the queued job at once, inside after(), and the reply waits up to fakeDrainWaitMs for it. prepareProviderEvent() looks up Ramble ids first if the event carried none.
  9. confirmOrder()Pure lib
    src/server/db/confirmOrder.ts
    Inside the job's transaction, under the session, hold and order locks. Decides with confirmDecision(): confirm the booking, report already_confirmed, or take the refund path (seats sold after a lapse). On confirm it calls revalidateTagsForChanges() for the session's spaces.
  10. router.push(orderConfirmationPath(reference, token))Client island
    src/components/CheckoutPage/CheckoutPage.tsx · src/lib/routes.ts
    onPaid runs when FakePaymentForm gets succeeded. The token travels as ?t=.
  11. OrderConfirmationPageServer
    src/app/(checkout)/(site)/orders/[reference]/page.tsx
    Picks the token from the cookie or ?t= (src/proxy.ts moves it into a cookie and redirects without it), calls readOrderPage(reference, token), and notFound() on any refusal. It passes getOrderStatus to OrderConfirmation as the poller for an order not yet confirmed.

What arrives when

  1. One render, per request. The root layout, frame, header, summary, form and footer arrive together. The route reads the hold and the settings in parallel, so the page waits on the slower of the two. There is no skeleton.
  2. Hydration. CheckoutPage wakes up as one island, with Header, OrderSummary, CheckoutForm and the panels inside it. CheckoutHoldTimer starts ticking from the server's clock.
  3. Later, on a tap. startPayment, then confirmFakePayment. Nothing is called on load or refresh, so reloading spends none of the hold's five tries.

Key user path through the actions

  1. Guest lands from the experience page's reserveSpaces, with the hold id in the address.
  2. Tap Continue: Server action startPayment. An answer of requires_payment moves the step to payment; already_confirmed routes straight to the order page; held to a fresh checkout.
  3. Tap Pay: Server action confirmFakePayment. succeeded calls onPaid and the router goes to the order page.
  4. Timer ends: the step becomes expired; Server action reholdSpaces offers the same spaces again.

Cache invalidation

The only cached read here is getCachedGuestSettings(), tagged settings and cleared when an ops user saves settings. The hold view is never cached. A confirmed payment calls revalidateTagsForChanges() from the job, and a re-hold or release calls updateTagsForChanges() from its action, both for the session's spaces change, which clears the session:<id> tag, so the space counts that the experience page shows are rebuilt. The webhook and job path uses revalidateTag(tag, 'max'), so one response after the call may still show the old count.

Worth knowing

  • There is no root src/app/layout.tsx. (checkout)/layout.tsx is the root layout and draws html and body. The (site) layout that serves orders, manage and gift does not wrap checkout.
  • The page is one big island. Header, OrderSummary, Alert, Input and the rest have no 'use client' but all ship as client code, because CheckoutPage imports them. The server page passes three server actions in as props, so the island never imports them.
  • The fake webhook is never an HTTP call. deliverFakeConfirmation() signs an event and calls takePaymentWebhook() directly in the same process. The route /api/webhooks/payments exists for a real provider (a TODO for U-046), and its secret is random per process, so a delivery nobody in this process signed is refused.
  • Paying and confirming the order are two separate steps. The webhook only stores the event and a job. confirmOrder() runs in the job, which the action drains in after() and waits for only a few seconds. If the drain is slow, the guest lands on the order page before the order is confirmed, which is why that page polls getOrderStatus.
  • The hold timer and the page's step share one reducer. onEnd from CheckoutHoldTimer dispatches into CheckoutPage's state, and showsHoldTimer(step) hides the timer in the header only on the sold_out step, so it stays visible beside the expired panel.
  • Unknown checkout addresses answer 200, not 404. /checkout and the catch-all call notFoundPerRequest(); the comment in renderPerRequest.tsx says the status cannot change once the render resumes from the empty shell. A bad hold id on the real route is also a rendered "not found" panel, not a thrown one.
  • The maintenance switch is read twice by two different functions. The page reads it through the cached getCachedGuestSettings(), while startCheckoutPayment() reads it through the uncached getGuestSettings(), so the action stays correct when the cached page is stale. A failed read fails closed.
  • No bot check on checkout. ADR 0007 keeps BotID off it; limits are the device's reserve tries and the hold's payment_tries.
