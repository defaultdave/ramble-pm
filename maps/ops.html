Ops back office map

Every page under src/app/(ops)/: the shared layout, the role gate, what each page reads and which actions it posts to, what gets written to the audit log, and which guest caches an ops change clears. Traced from the code on origin/main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache'. None on any ops page
Streamed behind a Suspense fallback
Client island 'use client', hydrates
Server action posted from a plain form
DB read / Pure lib a Postgres read in src/server/db, or a plain function in src/lib

Ops pages read the signed-in caller, so none is cached or prerendered. They render per request, and nothing below the layout's nav uses Suspense. Forms post straight to server actions and the result comes back as a ?notice= code on a redirect, so the pages need no client state.

The role gate

  1. Page. readOpsCaller() then holdsOpsRole(roles). Only the ops role passes; admin does not. A failure returns OpsAccessDenied with a Sign in link, status 200.
  2. Read. Every src/server/db function used here calls requireOpsUserId or requireRole(Role.Ops) again and throws ForbiddenError. The page check is a courtesy; this one is the gate.
  3. Action. opsCallerOrLeave(path) first. A non-ops caller is redirected to the list page, where they see the refusal. The proxy does not gate /ops; it only writes the CSP.
  4. Exceptions. The mailbox also admits a holder of the shared-secret cookie off production. The test console admits ops or admin, and shuts on a production deployment.

Audit logging

  1. Writes. Each change writes its audit row with writeAudit(tx) in the same transaction, so the row exists exactly when the change does. A change that differs by nothing writes neither.
  2. Reads. Sensitive reads are recorded with recordAudit before they return: ops home, hosts (list, one, new form), sessions (list, one), bookings (list, one), staff, support, audit view, mailbox (list, message, unlock).
  3. Not recorded. Experiences, review, availability, host suspension state, and the whole test console, including the demo data reset.

Render trees by area

Each subtree starts at the route page. Every page also does await Promise.all([searchParams, readOpsCaller()]), then the gate, then its reads. Gate shown only where it differs.

Approving an experience

  1. Review queue lists in_review experiences. A row opens /ops/review/<id>.
  2. Approve posts Server action approveExperienceAction. It checks the role, then decideExperienceReview locks the experience and refuses without photo alt text or with a suspended host.
  3. One audit row, then after the commit the listing tags clear with updateTag. The redirect goes to the queue with ?notice=approved.

Cancelling a session

  1. The session page reads the impact and hands the form a fingerprint of it in a hidden field.
  2. cancelOpsSessionAction refuses if the session ended, a booking cannot be refunded in full, or the fingerprint no longer matches what is true now.
  3. cancelSession releases holds, cancels and refunds each booking, queues emails. Then revalidateTag(..., 'max') for the session and experience, so the first guest request after may still see the old page.

Adding a host

  1. /ops/hosts/new shows the form (and records that it was opened).
  2. createHostAction parses, then createHost makes the host, the owner account (marked verified), the owner grant, the optional agreement acceptance and the audit rows in one transaction.
  3. inviteHostOwner emails a sign-in link. The redirect lands on the host's page. No guest cache is touched.

What an ops change clears in the guest caches

Ops pages hold no cache of their own. Their changes reach the guest side through tagsForChanges() in src/lib/cacheTags.ts. The experience page's shell and its upcoming dates carry experience:id; spaces left carries session:id; browse, the home cards and the host page carry catalog and the experience tags. updateTag makes the next request fresh. revalidateTag(tag, 'max') serves one stale response first.

Worth knowing

  • An ops host edit never reaches the host page. A host's own settings change clears catalog (hostProfile). The ops updateHost goes through saveHostFields and returns no cache change, so a new name or about text shows only when the catalog profile lapses (15 minutes to revalidate, a day to expire). src/server/hostPage.ts says so in a comment.
  • Session and booking cancels clear caches more weakly than edits. Edits, pauses, approvals and seat changes use updateTag. Both cancels use revalidateTag(..., 'max'), so one guest response afterwards can still show the cancelled session as bookable. The cancelSession comment says "Runs in a Server Action only (it invalidates cache tags)", which would allow the stronger call.
  • A non-ops visitor gets a 200 sign-in page, and an unknown address is a 200 too. OpsAccessDenied is returned, not thrown. The catch-all calls notFound() after connection(), and the comment in renderPerRequest.tsx admits the status stays 200 and the page appears only once script runs.
  • Reading the audit log writes to it. Opening /ops/audit, a blank new-host form, or the ops home each add a row. Experience, review and availability reads, and the entire test console including the demo data reset, write none.
  • The test console is not in the nav. opsNavLinks lists ten entries and no /ops/dev. It is the only page open to admin, and the only place a guard on the environment (VERCEL_ENV) decides what an action does.
  • The mailbox has no ops check of its own. Its page skips holdsOpsRole; loadMailbox decides, and unlockDevMailbox is the one ops action that does not call opsCallerOrLeave.
  • Forms work without script, yet every submit button hydrates. Button is a 'use client' file, so each form's button is a client component. The pages and views around it are server components, and ButtonLink deliberately is not.
  • The layout has its own root. (ops)/layout.tsx renders html and body. Nothing is shared with the guest layout, and RenderPerRequest sits beside the shell so no shell is prerendered.
