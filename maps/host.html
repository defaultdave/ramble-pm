Host area map

Every page under src/app/(host)/: one shared layout, a dashboard, and six more pages. The area is for signed-in hosts, has no cached reads and no Suspense boundary, and ships very little client code. Traced from the code on main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache' (none in this area)
Streamed behind a Suspense fallback (none in this area)
Client island 'use client', hydrates
Server action called from a form or island
Pure lib / server read function in src/lib or src/server, run per request

The role gate

  1. Not in the proxy or the layout. src/proxy.ts only sets the CSP nonce. The layout renders the shell for anyone, because a layout is not rendered again on a client navigation. So every page checks the caller itself.
  2. Page. A load...() function calls getCaller(), then hostAccessFor(), which reads the caller's own grants: signed_out, no_host_role, owner or staff. The host is the grant's host, never one from the address. An owner of several hosts gets the first granted; owning one and staffing another gives the owned one.
  3. Read. The read runs only if a host id came out, and the db function checks the role again (requireAnyRole for owner or staff, requireRole for owner).
  4. Answer. Signed out: redirect(signInHref(path)), which returns to the same page. No host role, staff on an owner-only page, a host that is gone, or a session that is not theirs: notFound(), drawn by NotFoundNotice, which does not say the area exists.
  5. Actions repeat it. Each action fetches the caller again and uses the grant's host, so a posted host id or session id from another host changes nothing.

What arrives when

  1. One wait. RenderPerRequest pins the area to per-request rendering and there is no Suspense, so nothing is prerendered. The reply starts after the page's caller lookup and database read finish.
  2. One piece. The shell, the page and all its rows arrive together as server HTML. A failed read shows the area's error page instead.
  3. Hydration. Button wherever a form uses it, plus PublishWeekForm, EditSessionForms and AddOneOffForm on the sessions page, and the error boundary if it shows. The dashboard, bookings and experiences pages have no island of their own.

Actions by page

  1. /host/sessions. Six actions through useActionState. Each returns a state (done, problem, invalid, failed) and the page refreshes with revalidatePath('/host/sessions').
  2. /host/settings. updateHostSettingsAction, a plain form post that ends in a redirect with ?notice=.
  3. /host/staff. Invite, resend and revoke: plain form posts that redirect with a notice code.
  4. Dashboard, bookings, guest list, experiences. No actions. The bookings search is a GET form.

What a host change clears in the guest caches

Host pages read the database every time, so their own pages need no clearing. These writes clear guest-side tags with updateTagsForChanges() (updateTag, so the next guest request sees the change) after the commit.

Worth knowing

  • The gate is repeated, not shared. The layout has no check by design, and each of the seven pages repeats the same three-line branch. Only the dashboard, experiences and settings loaders use loadForHostArea; the week, bookings, guest list and staff loaders rebuild the caller, access and host steps by hand. A new host page that forgets the branch would render for anyone, with the read the only thing stopping it.
  • The catch-all answers 200. An unknown /host/x shows the not-found page with status 200, and the page appears only once script runs (the empty shell has no heading). The code comment says why: a render resumed from the shell cannot change the status.
  • A capacity change clears less than a time or price change. It clears only session:<id>, not experience:<id>, so the experience page's cached data is not rebuilt by it.
  • Staff are stopped twice on owner pages. The page refuses them, and the db read needs host_owner. On sessions they get the page without forms, and publishing uses the owned host only.
  • Button is the common island. It is 'use client', so every host form that uses it (settings, staff, sessions, search) ships that code even though most of those forms are plain server <form action> posts.
  • Shared with ops. StaffView is the component ops staff admin uses; the host page passes managedRole="host_staff" and its own three actions.
  • Sign out needs no script. AccountControl is a server component with a plain form post, reused from the guest header.
