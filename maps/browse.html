Browse page map

How browse is assembled: the filters held in the address, the filter bar and drawer, the lazily loaded calendar, and the results. The two landing pages that reuse its results are mapped in the second half. Traced from the code on main, 2026-11-15.

Key

Server renders to HTML, no JS shipped
Cached read 'use cache', tagged for invalidation
Streamed per request, behind a Suspense fallback
Client island 'use client', hydrates
Server action called from an island
Pure lib plain function in src/lib

Filters live in the address

There is no filter state in the browser. The address is the state: category, neighborhood (both lists, up to 8), date, guests, price, age, setting, q and after, defined once in browseParamNames in src/lib/filters.ts. parseFilters() drops anything malformed, so a bad value is the same as an absent one, and sorts lists so one set of filters has one address. Every chip is a link to the address with that chip toggled. A page's cache key is the parsed filters plus the minute, so people with the same filters share one entry.

Shared with browse

The results tree (BrowseResults, the list island, the cards, BrowseSkeleton), getBrowseResults, getFilterOptions, the minuteAsOf clock and the connection() stream boundary.

Different

No filter bar, drawer, calendar or search, so none of those islands ship. Only two things are read besides the results: the editor's copy and the name. The heading and copy sit in the prerendered shell; only the experiences stream. No searchParams: the page has one filter, fixed by the address.

What arrives when (browse)

  1. Shell. Layout, header, the heading and intro, and the BrowseSkeleton in place of the bar and results.
  2. Streamed in. Banner and account, then BrowseContent: the filter bar and the first 12 cards land together, replacing the skeleton. They need searchParams and the clock.
  3. Hydration. SiteMenu, FilterRow with its buttons and date chip, WhenDetails, LazyDatePicker (placeholder only), the results list and Button. No filter works only through these: every chip, the search and Show more are plain links or forms.
  4. Idle. The drawer chunk and the calendar chunk are fetched when the browser is idle, or on first hover or focus of a chip, unless data saving is on.

Picking a day

  1. The guest opens the date chip. WhenDetails counts the open and LazyDatePicker fetches the calendar if the idle warm-up has not.
  2. Choosing a day calls Server action chooseBrowseDate in src/server/actions/browse.ts, bound to the current filters by BrowseContent.
  3. The action parses both the filters and the date again (both come from the browser), then redirect()s to the address with date set. There is no stored state. The new address renders, WhenDetails sees the date change and closes.

Every other filter, and the drawer's chips, navigate by link: they call no action.

Cache invalidation

The three schedule reads (getBrowseResults, getBrowseDates, suggestions) use the short browse profile (revalidate 60 s, expire 120 s) and carry catalog. A listing change (publish, edit, take-down) and hostProfile go through tagsForChanges() in src/lib/cacheTags.ts and clear catalog, which clears all of them. getBrowseResults also tags each experience it shows, so an experience change (sessions or photos) clears the pages that list it. A session added to an experience that is on no cached page waits for the minute to run out. Category and neighborhood names (taxonomy) are never invalidated: no change reaches that tag, so a rename shows when the editorial profile runs out. Landing copy has its own tags, category:<slug> and neighborhood:<slug>, cleared by the categoryCopy and neighborhoodCopy changes, and by a listing change for that listing's own category or neighborhood.

Worth knowing

  1. One boundary holds both bar and results. The filter bar sits inside BrowseContent, so on a first load it waits for the same reads as the cards and the skeleton stands in for both. The bar is not independent of the results: a failed read replaces it with the error view.
  2. The calendar is loaded two ways and mounted twice. It appears in the chip row and, inside the drawer, again as its own WhenControl. The drawer mounts its copy fresh each time it opens, which is why loadedDatePicker() hands an already-fetched module to a late mount.
  3. Shared state between islands is small. FilterRow shares open and busy with its buttons through a context. datePickerLoader.ts holds one module-level variable that every LazyDatePicker and the warm-up read. WhenDetails passes the open count to the picker by context.
  4. The drawer's chips are not controlled inputs. They are links built on the server. "Show results" only closes the drawer, since pressing a chip has already navigated. The button cannot say how many results, and the code says so.
  5. NoScriptFilters and BrowseResultsList are client files for a render reason, not interactivity. Both exist to keep the markup from being streamed as templates (noscript content, and a row past about 3,200 bytes). The card code ships to the browser as a result.
  6. The server action takes filters from the browser. chooseBrowseDate.bind(null, filters) sends the filters through the client, so the action re-validates all of them.
  7. Landing results share browse's cache. landingQuery() is the first page of one filter, which is a query browse also issues for ?category=x, so the entry can be shared.
  8. A landing page's "Show more" leaves the landing page. The landing view reuses browseView(), whose targetFor() posts to browsePath with the category or neighborhood and after. The second page is therefore browse, not another landing page. Its empty state is the exception: landingView() rewrites it so it is not "filtered".
  9. Page title reads options a second time. generateMetadata calls getFilterOptions() through getBrowseTitle() as well; the same cached entry, so no extra database read.
