### Blocking

- src/lib/audit.ts:174 (used at 187, 188, 197): `dayOf` is `date.toISOString().slice(0, 10)`, the same function as `isoDateOf` in src/lib/time.ts:24, which this file already imports from (`msPerDay`, `msPerMinute`). - src/lib/audit.ts:70-79 (DetailsSchema): the lib repairs input instead of failing closed, and disagrees with the database. Verified by running it: `parseAuditEntry` with `details = JSON.parse('{"__proto__":"Ada Lovelace","ok":1}')` is accepted and returns `{"ok":1}`; `{"__proto__":{"x":1}}` returns `{}`. Zod's record silently skips a `__proto__` key, so the key never reaches the key rule, and `writeAudit` inserts a different row from the one the caller passed. The database, given the original object, refuses it (key fails `^[a-z][a-z0-9_]{0,39}$`; probed). Reachable only when details come from `JSON.parse`, but the table is the one place a silent change to a row can never be corrected, and the rule is "database refuses what the lib rejects, and the lib repairs nothing". Fix: in the `DetailsSchema` custom check, also refuse `Object.hasOwn(value, '__proto__')`, and add that case to the lib and `it.each` parity tables (`['a __proto__ key', JSON.parse('{"__proto__":1}'), false]`).

- src/server/jobs/registry.ts:84 with src/server/jobs/auditSchedule.ts:10-12: a dead export day is lost for good, and the comment promises a recovery nothing provides. `jobs_dedupe_key_unique` covers every status (src/server/db/jobs.ts insertJob, enqueue.ts doc "the key stays used after the job finishes"), so once `audit-export:<day>` dies the scheduler's `enqueue` returns null for it every pulse. "Ops re-runs that day by hand" has no builder: no unit in units.yaml re-drives dead jobs, and `enqueue` cannot do it. The retry budget is `defaultMaxAttempts` (8) with a 30 s doubling backoff, but jobs run only on the 30-minute pulse, so a storage outage of roughly 3.5 to 4 hours kills the day. The scheduler comment and the lib doc (`exportDaysDue`: "an outage shorter than the lookback catches up") are true only for a pulse outage, not for the failure this export exists to survive. Fix (do at least the first two): (a) set this job's `maxAttempts` to `jobLimits.maxAttemptsCeiling` (20; about 2.5 days of retries at the 6 h cap) with a test on the registry value; (b) change the comment to say what is true and name the unit that will re-drive with `TODO(U-xxx)` (PM to add one to units.yaml; B7 and CLAUDE.md need a real unit id), or have the scheduler enqueue `audit-export:<day>:r<n>` for a day whose job is dead, bounded by the lookback.
